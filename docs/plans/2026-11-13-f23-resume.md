### 1.2 Problem

A `decoy run --chunked` over many large tables that fails at table 18 (disk full, a bad row in
one source, Ctrl-C, SIGKILL, a reboot) has to start again from table 1. After DELIV it is worse
in one way: strict delivery stages every table and removes the stage on failure, so even the
files of the 17 finished tables are gone. The owner wants a long run to continue from the last
finished table (UX map Q12, spec F23 example 1).

## 2. Guarantee

> `decoy run PIPELINE --resume RUN_DIR` continues a failed, interrupted or killed `--chunked` run
> in the same run id. Every table whose checkpoint verifies is kept byte for byte and is not read,
> masked or written again; every other table runs again from its start. The delivered result is
> the result an uninterrupted run with the same inputs would have delivered, or nothing is
> delivered and the run refuses with a value-free reason. A resume never mixes outputs made under
> a different config, engine, key, chunk size or source content, and never moves `LATEST`
> backwards.

Non-goals (each a V2-LOG line in section 13): the plain route; chunk-level resume; `--out-dir`,
absolute targets and cloud targets; adding tables to a run already delivered (best-effort
partial); automatic removal of checkpoints never resumed; Windows crash claims; platform resume.

## 3. Established solutions

Search run (2026-11-13): dbt `retry`, Airflow task clear, Spark Structured Streaming checkpoints
(web); in the codebase the F22 descriptor and `publish_unit`, DELIV's stage and CAS, `_atomic.py`.

- **dbt `retry`** reads the previous run's `run_results.json` and re-executes only the nodes that
  errored or were skipped; nodes that succeeded are not rebuilt; after a successful run it is a
  no-op; a run that failed before any node ran has nothing to retry
  (docs.getdbt.com/reference/commands/retry). Followed: the keep and rerun split per table, the
  no-op on a delivered run (OQ-5), the empty-store refusal.
- **Airflow clear** with "Downstream" and "Only failed" resets the failed task instances inside
  the same DAG run and leaves successful ones (astronomer.io/docs/learn/rerunning-dags).
  Followed: resume continues the same run id, not a new run.
- **Spark Structured Streaming** keeps an offset log and a commit log per query; on restart a
  batch counts as finished only when its commit file exists, and only the existence of that file
  is the proof; a query may not change between restarts from one checkpoint, and two queries must
  never share one location (docs.databricks.com/en/structured-streaming/checkpoints). Followed:
  the activation record written last is the only proof a table finished (UX map 6.1 asks the
  same); a fingerprint mismatch refuses; one lock per checkpoint store.
- **Key check value** (KCV, payment HSM practice: a short MAC of a fixed block under the key)
  proves "same key" without storing the key. Followed for the key part of the fingerprint.
- **Durable link then record**: the PostgreSQL `durable_rename` order (fsync file, link or
  rename, fsync directory), already in `src/decoy/_atomic.py:3-5` and F22 5.0.

Custom code left: the store layout and the keep rule (`plan_resume`), both small. No library
gives a resumable table checkpoint for a local CLI.

## 4. Design

### 4.1 Unit and route

The checkpoint unit is one mask table on the chunked route. The CLI owns that loop, each table is
independent of the others (value-keyed strategies only), and the route has no vault, quarantine,
generation or post-scan integrity. So a finished table needs only its own file to be reused: no
vault boundary, no generator state, no cross-table frame in memory.

UX map 6.1 asks for the vault to be durable per table and for the activation record to bind a
vault boundary. On this route there is no vault (B-6 refuses it), so V1 does not build that part.
A defensive refusal (`resume_vault_unsupported`) stops a resume of any config that carries a vault
writer, so a later route change cannot reuse output whose vault was lost (OQ-3).

UX map 6.1 also asks that tables with unseeded random strategies always re-run. That rule is for a
partial unit (chunk-level). A whole finished table needs no repeatability to be kept, and such
strategies cannot run chunked anyway (`check_chunked_compatibility`). No rule is built for it.

### 4.2 Store layout

The store sits beside the run folder, on the same filesystem as DELIV's stage, so a hard link
keeps a staged file without a copy:

```
out/<name>/.<run-id>.decoy-resume/                     0700, create_private_directory
    RUN.json                                           decoy-resume-run/v1, written once, first
    tables/<index>-<12 hex of sha256(name)>.<ext>      hard link of the staged output file
    tables/<index>-<12 hex of sha256(name)>.json       decoy-resume-table/v1, written last
```

Inside the run folder is not possible: F22 binds a stage only onto an absent or empty leaf (F22
5.3), so files there would turn the bind into `publication_target_occupied`. File names carry the
table index and a digest of the name, never the name itself.

`RUN.json` (`decoy-resume-run/v1`): `schema`, `run_id`, `operation_id` (the F22 id the run's
`DeliveryStage` was opened with), `route` (`chunked`), `fingerprint` (4.3), `tables` (the mask
tables in config order, each `{index, name_digest}`).

`<index>-<digest>.json` (`decoy-resume-table/v1`): `schema`, `index`, `name_digest`, `artifact`
(F22 `Artifact`: `path` relative to the run folder, `role` `table`, `rows`, `sha256`, `size`),
`source_sha256`, `fingerprint_digest`.

Both records use F22's canonical JSON and strict reader rules (F22 5.2: exact tag, every field,
no unknown field, exact types, hex by `fullmatch`; cap 64 KiB). A record that fails the reader
counts as absent.

### 4.3 Fingerprint

`RunFingerprint` (engine `resume/_fingerprint.py`), every field value-free:

| Field | From | Why |
|---|---|---|
| `config_hash` | `pipeline_config_hash` (engine `plan/__init__.py:37`); covers the seed, the strategies, targets, formats and `delivery.mode` | any config change changes output |
| `seed_protocol_version`, `profile_hash` | the compiled `Plan` (engine `plan/_types.py:297-300`) | the determinism envelope |
| `engine_version`, `cli_version`, `pyarrow_version` | the running packages | the CSV writer is CLI code; Parquet bytes depend on pyarrow (`_execute.py:76-81`, the `_run_chunked_mask` docstring) |
| `key_check`, `key_version` | `HMAC-SHA256(key_provider.mask_key(), b"decoy-resume-key-check/v1")`, first 16 hex | same key, without storing it |
| `chunk_size` | the run's chunk size | Parquet row groups follow it |

`fingerprint_digest` is the sha256 of its canonical JSON. Per-table source identity is not in
the run fingerprint: each table record stores `source_sha256`, the streamed sha256 of that
table's source file taken just before its chunk loop (1 MiB blocks). Size and mtime are not used
(UX map 6.1).

### 4.4 Writing checkpoints (the first attempt and every resumed one)

In the chunked loop, in this order:

1. Before the first table: take the store lock (4.6), write `RUN.json` (`write_atomic`, fsynced).
2. Per table: `source_sha256` of the table's source.
3. The table runs and is written into the stage through the sink (DELIV), unchanged.
4. `sink.on_table_staged(name)` returns the staged path. Fsync the file, `os.link` it into
   `tables/`, fsync `tables/`.
5. Measure `size`, `sha256` and `rows` from the linked file, then write the activation record
   with `write_atomic` (fsync file and directory). This record is the only proof the table
   finished.
6. After DELIV's visibility point (`LATEST` swapped): remove the store. A failure here is a
   warning (`resume_store_not_removed`), never a change of exit.

On a caught failure or Ctrl-C the sink aborts its stage as today; the store is kept, and the
summary prints one line: `resume with: decoy run <pipeline> --resume out/<name>/<run-id>`
(project-relative, value-free). After SIGKILL the store is simply there.

### 4.5 Resume

`decoy run PIPELINE --resume RUN_DIR`, with the pipeline argument the user gives today (OQ-6).
`RUN_DIR` is `out/<name>/<run-id>`; the folder itself may be absent, because `abandon()` removes
a failed run's empty folder. Order:

1. Resolve: the parent must be this pipeline's `out/<name>/` and the leaf must pass `is_run_id`
   (`_layout.py:77`), else `resume_run_dir_invalid`. Refuse `--out-dir`, absolute targets and
   cloud targets (`resume_layout_unsupported`, OQ-2), a run without `--chunked`
   (`resume_route_unsupported`, OQ-1) and a vault writer (`resume_vault_unsupported`).
2. Take the store lock without waiting; held: `resume_in_progress`. No store: if the run folder is
   bound (a valid F22 descriptor), print "already delivered" and exit 0 (OQ-5); else
   `resume_no_checkpoint`.
3. Read `RUN.json` (invalid: `resume_store_invalid`). Read `LATEST`; a run id later than this one:
   `resume_superseded` (a resume must not move `LATEST` back; DELIV's CAS would also refuse at
   deliver, this says so before any work).
4. Build the current fingerprint; any field different: `resume_fingerprint_changed`, naming the
   field (`config_hash`, `engine_version`, and so on), never a value.
5. For each table with a valid activation record: recompute the linked file's `sha256` and size,
   and the source's `sha256`. Call `plan_resume` (4.7).
6. Reopen the run: `RunLayout.open(..., run=RunFolder(path, run_id))` with the existing empty
   folder, or a new 0700 one when it was removed; open `DeliverySink` with the stored
   `operation_id`.
7. Kept tables: `sink.adopt_table(name, linked_file)` links the file into the new stage at the
   target's placed path (copy when `link` fails with `EXDEV` or `EPERM`, then re-hash the copy)
   and records the table `ok`.
8. Rerun tables: the chunked loop of 4.4, writing new checkpoints.
9. Deliver as DELIV does. A crash after bind and before `LATEST` leaves the store in place; the
   next resume keeps every table, F22 judges the bound unit `already_committed` (equal
   `result_id`) and DELIV swaps `LATEST` (DELIV 7.1).

### 4.6 Locks

One `flock` on the store directory (`_folder_lock`, `src/decoy/_atomic.py:623`), taken by the
first attempt when it creates the store and by each resume at step 2, held until the process
ends. Order: store lock, then DELIV's pointer lock, then F22's run-id lock (DELIV 4.5 says F23
takes the same order). Nothing takes the store lock while it holds either of the others.

### 4.7 `plan_resume` (engine, pure)

Input: the stored and current fingerprints, the config's mask-table order, and per table a
`TableCheck(record_valid, artifact_ok, source_ok)`. Output: `ResumePlan(keep, rerun, warnings)`,
or `ResumeRefusedError(code, field)`.

| Case | Result |
|---|---|
| a fingerprint field differs | refuse `resume_fingerprint_changed` |
| the table set or order differs from `RUN.json` | refuse `resume_fingerprint_changed` (`tables`) |
| record valid, artifact ok, source ok | keep |
| record valid, artifact missing or digest differs | rerun, warning `resume_checkpoint_invalid` |
| record valid, source digest differs | refuse `resume_source_changed` (a kept table would come from another snapshot) |
| no record, or record invalid | rerun |
| nothing to rerun | keep all, deliver (crash between the last record and bind or `LATEST`) |

The keep rule has no relationship closure: chunked tables are masked independently by
value-keyed strategies, so a kept parent and a rerun child agree on every key, as they do in an
uninterrupted chunked run (AT-R6 pins it).

### 4.8 Reason codes

Engine `reasons/decoy/_resume.py`, registry minor by the renumber rule (roadmap 5.2 rule 1).
Refusals, category `usage`, exit 1: `resume_run_dir_invalid`, `resume_layout_unsupported`,
`resume_route_unsupported`, `resume_vault_unsupported`, `resume_in_progress`,
`resume_no_checkpoint`, `resume_store_invalid`, `resume_superseded`,
`resume_fingerprint_changed`, `resume_source_changed`. Warnings: `resume_checkpoint_invalid`,
`resume_store_not_removed`. The CLI raises the engine's `ResumeRefusedError(code, field=None)`;
RESULT's `_errors.py` maps it through `derive_outcome` like any usage error. No code string is
copied into the CLI (`tests/sentry/test_engine_reason_code_copies.py`).

### 4.9 Output

- `--json` gains one member, `resume`: `{run_id, kept: [names], rerun: [names], invalid: [names]}`
  (names through `approve_name`), present only with `--resume`. Additive.
- The run summary gains one line: `resumed run <run-id>: kept 17 tables, ran 3`.
- `decoy-run-result/v1` is unchanged (RESULT's rule: no `_model.py` edit). Resume facts in the
  run-result document are a V2-LOG line.

### 4.10 Design notes

- New structure: one engine package `resume/` (pure: types, codec, decision) and one CLI module
  `src/decoy/cli/io/_checkpoint.py` (the only writer and reader of the store). Principle: one
  place per fact; the record shape lives once, in the engine, and the CLI never builds a record
  dict. Change pain addressed: platform resume later reads the same records and calls the same
  `plan_resume`.
- Choke point: every checkpoint write goes through `CheckpointStore.record_table`; every reuse
  goes through `CheckpointStore.verified_tables` and then `plan_resume`. Guard:
  `tests/sentry/run/test_one_checkpoint_store.py` walks the import graph and the syntax tree and
  fails when a module other than `io/_checkpoint.py` names a `decoy-resume-` tag, imports
  `decoy_engine.resume` record encoders, or calls `os.link`. Mutation: write a record from
  `run/_execute.py` directly.
- House style: a typed `ResumeContext` on `RunContext`, not new parameters on `execute`; no flag
  argument switches the chunked loop (resume passes a `keep` set, empty on a first attempt).

## 6. Failure modes

### 6.1 Class table

| # | Class | Structure that closes it | Proof | Mutation that turns it red |
|---|---|---|---|---|
| 1 | Value-bearing output | records carry digests, counts and the name digest; refusals name a field, never a value; names through `approve_name` | AT-V1 canary | put the table name in a file name |
| 2 | Cleanup missing on an exit path | the store is removed only after the visibility point and kept on every other exit; the stage is aborted by DELIV's sink as today | AT-K5, AT-K2g | remove the store in `finally` |
| 3 | State and concurrency | link and fsync before the record; record by `write_atomic`, the only proof a table finished (Spark commit log); one `flock` per store, non-blocking, held for the process | AT-S2, AT-L1, AT-K2a to AT-K2d | write the record before the link; take the lock with a wait |
| 4 | Route parity and silent fallback | only the chunked route writes a store; every other route, layout kind and a vault config refuses `--resume` with a named code, never a silent full rerun | AT-R1 (B11, B14) | let a plain-route resume fall through to a fresh run |
| 5 | Referential integrity | value-keyed chunked strategies give a kept parent and a rerun child the same keys; a changed table set or order refuses | AT-R6, AT-P5 | ignore table order in `plan_resume` |
| 6 | Untrusted producer | both records go through the strict reader; an invalid record counts as absent, never partly used; `RUN_DIR` goes through the layout resolver | AT-C2, AT-R1 | accept an unknown field |
| 7 | Check then use (TOCTOU) | a kept file is re-hashed at reuse and that same file is linked; sources are re-hashed at resume; `LATEST` is read before work and DELIV's CAS checks it again at deliver | AT-P4, AT-R3, AT-R4, AT-R1 (B9) | trust the record's size without re-hashing; skip the `LATEST` read |
| 8 | Weak tests and overclaimed evidence | each AT names its mutation; mutations rerun on the final head; AT-R2 compares bytes with an uninterrupted run | gate reviewers rerun them | an AT green under its mutation; AT-R2 relaxed to row equality |
| 9 | Behaviour-preserving refactor drift | a first attempt with an empty keep set runs the chunked loop exactly as before; base outputs pinned before C1 | AT-K1 (files byte-equal to a clean run) | change the chunk loop order |
| 10 | Frozen contract drift | `--json` additive; run-result unchanged; exits from the existing map; two new persisted tags in the compat corpus | AT-X1, AT-C1 | add `resume` to the run-result model |

## 11. Open questions (owner)

- **OQ-1. The plain route.** `run_pipeline` returns every table at once, so a plain run has no
  finished table before it returns. Options: (a) V1 checkpoints the chunked route only; a plain
  run writes no store and `--resume` on it refuses `resume_route_unsupported` with "use --chunked
  for resumable runs"; (b) add a per-table output hook inside `run_pipeline` on every route
  (stream, sequential, full-frame, out-of-core, native), about 4 to 6 more engine slices with
  route-parity risk, the same work DELIV logged as V2 (its Q2 b, per-table isolation inside
  `run_pipeline`). **Recommended: (a).** The long runs resume exists for are the chunked ones.
- **OQ-2. `--out-dir`, absolute targets and cloud targets.** The fixed folder has no run id and
  rolls its temps back at the next open (DELIV 4.3); cloud stages live in the bucket.
  **Recommended: refuse in V1** (`resume_layout_unsupported`), V2-LOG.
- **OQ-3. Per-table durable vault (UX map 6.1).** Chunked runs refuse a vault, so no kept table
  has vault entries. **Recommended: do not build the vault boundary in V1**; resume refuses any
  vault config; the boundary comes with chunk-level resume or a chunked vault.
- **OQ-4. Store retention.** A store never resumed stays in `out/<name>/` (hard links, so it
  holds the finished tables' bytes). **Recommended: keep it until a resume delivers or the user
  deletes it; the hint and `decoy explain resume` say so; sweeping belongs to F26.**
- **OQ-5. Resume of a run already delivered.** **Recommended: exit 0, "already delivered",
  nothing written** (dbt `retry` is a no-op after success), also for a best-effort partial run,
  whose summary already named the dropped tables.
- **OQ-6. The pipeline argument.** **Recommended: required, as for any `decoy run`; a different
  config refuses naming `config_hash`.** Reading the config path from the store would let a moved
  or edited file run without the user naming it.

## 12. Recurring-defect walk (`/home/cam/dev-rules/catalogs/recurring-defects.md`)

1. Anchored validation: digests, run ids and tags by `re.fullmatch`; AT-C2 has the `"\n"` cell.
2. Strict stored types: both records refuse `bool` and numeric strings (AT-C2).
3. No exception context: `ResumeRefusedError` is raised after the `except` closes; AT-R1 asserts
   `__cause__` and `__context__` are `None`.
4. Versioned read models: exact tag, missing tag refused, one writer model with the reader
   derived from it (as F22 a2).
5. Normalized guard scanners: the checkpoint sentry resolves `import os` / `from os import link`
   / aliases; seeded cases per spelling.
6. No private imports: the CLI imports `decoy_engine.resume` and `decoy_engine.publication`
   public names only.
7. No hidden CI failures: no new CI job.
8. One trust class per entry point: `RUN_DIR` is user input and goes through the layout resolver
   (`is_run_id`, the pipeline's `out/<name>/`); store file names are program names.
9. Mutations on the final head: recorded per slice.
10. Allowlisted helpers: the sentry allows `io/_checkpoint.py` by exact path.
11. No raised caps: `io/_layout.py` must not need a cap change (stop line).

Value-free class (F31): records hold digests, counts and the name digest; refusals name fields;
AT-V1 is the canary. Check then use: a kept file is re-hashed at reuse and linked by the same
path inside a 0700 store the user owns; a swap between hash and link is a named limit.
