### 1.2 Problem

A `decoy run --chunked` over many large tables that fails at table 18 (disk full, a bad row in
one source, Ctrl-C, SIGKILL, a reboot) has to start again from table 1. After DELIV it is worse
in one way: strict delivery stages every table and removes the stage on failure, so even the
files of the 17 finished tables are gone. The owner wants a long run to continue from the last
finished table (UX map Q12, spec F23 example 1).

## 2. Guarantee

> `decoy run PIPELINE --resume RUN_DIR` continues a failed, interrupted or killed `--chunked` run
> in the same run id. Every table whose checkpoint verifies is kept byte for byte: its source is
> read once to verify its digest, and it is not masked or written again. Every other table runs
> again from its start. The delivered result is the result an uninterrupted run with the same
> inputs would have delivered, or nothing is delivered and the run refuses with a value-free
> reason. A resume never mixes outputs made under a different config, source or target binding,
> component version, key or chunk size, or source content, and never moves `LATEST` backwards.

Non-goals (each a V2-LOG line in section 13): the plain route; chunk-level resume; `--out-dir`,
absolute targets, cloud targets and `--duckdb-source`; platforms without `fcntl` (Windows);
adding tables to a run already delivered (best-effort partial); automatic removal of stores never
resumed; platform resume.

## 3. Established solutions

Search run (2026-11-13): dbt `retry`, Airflow task clear, Spark Structured Streaming checkpoints
(web); in the codebase the F22 descriptor and `publish_unit`, DELIV's stage and CAS, `_atomic.py`,
the generation `PinnedEnvelope` and the evidence manifest (7a).

- **dbt `retry`** reads the previous run's `run_results.json` and re-executes only the nodes that
  errored or were skipped; nodes that succeeded are not rebuilt; after a successful run it is a
  no-op; a run that failed before any node ran has nothing to retry
  (docs.getdbt.com/reference/commands/retry). Followed: the keep and rerun split per table, the
  no-op on a delivered run (OQ-5), the empty-store refusal.
- **Airflow clear** with "Downstream" and "Only failed" resets the failed task instances inside
  the same DAG run and leaves successful ones (astronomer.io/docs/learn/rerunning-dags).
  Followed: resume continues the same run id, not a new run.
- **Spark Structured Streaming** keeps an offset log and a commit log per query; on restart a
  batch counts as finished only when its commit file exists, and only the existence of that file
  is the proof; a query may not change between restarts from one checkpoint, and two queries must
  never share one location (docs.databricks.com/en/structured-streaming/checkpoints). Followed:
  the activation record written last is the only proof a table finished (UX map 6.1 asks the
  same); a fingerprint mismatch refuses; one lock per checkpoint store.
- **Key check value** (KCV, payment HSM practice: a short MAC of a fixed block under the key)
  proves "same key" without storing the key. Followed for the key part of the fingerprint.
- **Durable link then record**: the PostgreSQL `durable_rename` order (fsync file, link or
  rename, fsync directory), already in `src/decoy/_atomic.py:3-5` and F22 5.0.

Custom code left: the store layout and the keep rule (`plan_resume`), both small. No library
gives a resumable table checkpoint for a local CLI.

## 4. Design

### 4.1 Unit and route

The checkpoint unit is one mask table on the chunked route. The CLI owns that loop, each table is
independent of the others (value-keyed strategies only), and the route has no vault, quarantine,
generation or post-scan integrity. So a finished table needs only its own file to be reused: no
vault boundary, no generator state, no cross-table frame in memory.

Which tables the loop runs is decided in one place: `chunked_mask_tables(config_dict)` (in
`run/_execute.py`, C1) returns the `(index, name, source spec, target spec)` entries the loop
masks today, taking over the skips at `_execute.py:104-114` (no columns, no source path, no
target path). The loop and the store both iterate it; nothing else lists chunked tables.

UX map 6.1 asks for the vault to be durable per table and for the activation record to bind a
vault boundary. On this route there is no vault (B-6 refuses it), so V1 does not build that part.
A defensive refusal (`resume_vault_unsupported`) stops a resume of any config that carries a vault
writer, so a later route change cannot reuse output whose vault was lost (OQ-3).

UX map 6.1 also asks that tables with unseeded random strategies always re-run. That rule is for a
partial unit (chunk-level). A whole finished table needs no repeatability to be kept, and such
strategies cannot run chunked anyway (`check_chunked_compatibility`). No rule is built for it.

### 4.2 Store layout

The store sits beside the run folder, on the same filesystem as DELIV's stage, so a hard link
keeps a staged file without a copy:

```
out/<name>/.<run-id>.decoy-resume/                     0700, create_private_directory
    RUN.json                                           decoy-resume-run/v1, written once, first
    tables/<index>-<12 hex of sha256(name)>.<ext>      the staged output file, linked in
    tables/<index>-<12 hex of sha256(name)>.json       decoy-resume-table/v1, written last
```

Inside the run folder is not possible: F22 binds a stage only onto an absent or empty leaf (F22
5.3), so files there would turn the bind into `publication_target_occupied`. File names carry the
table index and a digest of the name, never the name itself.

`RUN.json` (`decoy-resume-run/v1`): `schema`, `run_id`, `invocation_id` (of the first attempt,
4.9), `operation_id` (the F22 id the run's `DeliveryStage` was opened with), `route` (`chunked`),
`fingerprint` (4.3), `tables` (the `chunked_mask_tables` entries in order, each `{index,
name_digest, binding_digest}`).

`<index>-<digest>.json` (`decoy-resume-table/v1`): `schema`, `index`, `name_digest`,
`binding_digest`, `artifact` (F22 `Artifact` as measured by F22: `path` relative to the run
folder, `role` `table`, `rows`, `sha256`, `size`), `source_sha256`, `fingerprint_digest`.

The artifact `path` is the target's placed path relative to the run folder, the same trust class
as the F22 descriptor that the delivered run folder carries anyway (AT-V1 scopes the name canary
to store file names for this reason).

Both records use the engine's canonical JSON (`decoy_engine.records.canonical_bytes`) and F22's
strict reader rules (F22 5.2: exact tag, every field, no unknown field, exact types, hex by
`fullmatch`; cap 64 KiB). A record that fails the reader counts as absent.

### 4.2a One durable link helper

`tests/sentry/test_atomic_writer.py` forbids `os.link` outside `src/decoy/_atomic.py`, and
`_atomic.py:134` already names the errnos that mean "this mount has no hard links"
(`_NO_HARD_LINKS`). C0 adds one public helper there:

`durable_link_or_copy(src: Path, dest_dir: Path, name: str) -> None`: fsync `src`; `os.link` it
to a temp name in `dest_dir`; on an errno in `_NO_HARD_LINKS`, copy to the temp name and fsync it
instead; `os.replace` the temp onto `name` (so an orphan from an earlier crash, K2b, is replaced,
not an `EEXIST`); fsync `dest_dir`. `EXDEV`, `ENOSPC` and any other errno are faults and raise;
there is no silent copy across filesystems. Both callers use it: the store's `record_table` and
the sink's `adopt_table`.

### 4.3 Fingerprint

`RunFingerprint` (engine `delivery/resume/_fingerprint.py`), built by
`build_fingerprint(config, key_provider, *, chunk_size, components)`, every field value-free:

| Field | From | Why |
|---|---|---|
| `config_hash` | `pipeline_config_hash` (engine `plan/__init__.py:37`). It covers masking semantics only: `_hash_config` drops `sources`, `targets`, `pre_scan` and `name` (`plan/_compile.py:625-650`) | strategy, seed and `delivery.mode` changes |
| `binding_digest` per table | `sha256(canonical_bytes({"source": sources[name], "target": targets[name]}))` with the engine's existing canonical JSON; no new hasher | the dropped binding: source path or format, target path or format |
| `components` | sorted `(distribution, version)` pairs from `importlib.metadata.version` for `decoy`, `decoy-engine`, `pyarrow`, `pandas`, `numpy`, `faker` | the CSV writer is CLI code; Parquet bytes depend on pyarrow; pandas is pinned as a range and is a documented determinism hazard; the engine version also pins the seed protocol |
| `key_check`, `key_version` | `HMAC-SHA256(mask_key_from_provider(key_provider, job_seed), b"decoy-resume-key-check/v1")`, first 16 hex; `mask_key_from_provider` is engine `keyprovider.py:256`, so the seed path (provider `None`) is covered; `job_seed` comes from the engine's own job-seed derivation for the config, never a CLI copy | same key, without storing it |
| `chunk_size` | the run's chunk size | Parquet row groups follow it |

`profile_hash` and `seed_protocol_version` are not fields: the chunked route never compiles a
`Plan` in the CLI and uses no profile, and the engine version in `components` fixes the seed
protocol. `fingerprint_digest` is the sha256 of the canonical JSON of the run-level fields.

Per-table source identity: each table record stores `source_sha256`, the sha256 of the table's
source file taken just before its chunk loop, through the CLI's existing `hash_file`
(`cli/evidence.py:140`; C0 STEP ZERO checks `.importlinter` lets `cli/io` import it, and if not
moves it unchanged to `src/decoy/_digest.py` per the CODEMAP "private shared primitives" row and
repoints `evidence.py`). Size and mtime are not used (UX map 6.1).

### 4.4 Writing checkpoints (the first attempt and every resumed one)

In the chunked loop, in this order:

1. Before the first table: take the store lock (4.6), write `RUN.json` (`write_atomic`, fsynced).
2. Per table from `chunked_mask_tables`: `source_sha256` of the table's source.
3. The table runs and is written into the stage through the sink (DELIV), unchanged.
4. `sink.on_table_staged(name)` returns the staged path and F22's measured `Artifact` for it (the
   measure F22 uses for the descriptor, so the record and the descriptor agree by construction).
   `durable_link_or_copy` puts the file into `tables/`.
5. Write the activation record with `write_atomic` (fsync file and directory). This record is the
   only proof the table finished.
6. After DELIV's receipt says `delivered` (the visibility point passed): remove the store by an
   atomic rename to `out/<name>/.<run-id>.decoy-resume.trash-<8 hex>`, then delete that tree. A
   receipt `uncertain` keeps the store. A failure to rename or delete is a warning
   (`resume_store_not_removed`), never a change of exit.

An empty table (an empty CSV source that publishes nothing, `_execute.py:84-85`) writes no
record and always reruns: it costs nothing and needs no `artifact: null` case.

On a caught failure or Ctrl-C the sink aborts its stage as today; the store is kept. It holds a
full masked copy of every finished table on disk until a resume delivers or the user deletes it
(the guide and `decoy explain resume` say so). The summary prints one line, the exact command to
continue: `resume with: decoy run <pipeline> --resume out/<name>/<run-id>` (project-relative,
value-free), plus, when `--mask-secret` was given, `pass the same --mask-secret as this run`.
After SIGKILL the store is simply there.

### 4.5 Resume

`decoy run PIPELINE --resume RUN_DIR`, with the pipeline argument the user gives today (OQ-6).
`RUN_DIR` is `out/<name>/<run-id>`; the folder itself may be absent, because `abandon()` removes
a failed run's empty folder. Order:

1. Resolve, through the `decoy.cli.io` facade: the parent must be this pipeline's `out/<name>/`
   by `same_path` and `_same_dir` (`io/_layout.py:90`, `:107`), and the leaf must pass
   `is_run_id` (`:77`), else `resume_run_dir_invalid`. The store path is built from the validated
   leaf name, never from the raw argument. Refuse `--out-dir`, absolute targets and cloud targets
   (`resume_layout_unsupported`, OQ-2), `--duckdb-source` (`resume_layout_unsupported`: each
   attempt exports a fresh temp source), `--rows`, `--sample` and report flags (usage), and a vault
   writer (`resume_vault_unsupported`). The route and the chunk size come from `RUN.json`:
   `--resume` implies `--chunked` and the stored `--chunk-size`; an explicit `--chunk-size` that
   differs refuses `resume_fingerprint_changed` (`chunk_size`). A store whose `route` is not
   `chunked` refuses `resume_route_unsupported` (OQ-1).
2. Delivered check first: if the run folder holds a valid F22 descriptor and `LATEST` names this
   run id or a later one, print "already delivered", remove the store if one is left (4.4 step
   6), exit 0 (OQ-5). Then take the store lock without waiting; held: `resume_in_progress`. No
   store: `resume_no_checkpoint`.
3. Read `RUN.json` (invalid: `resume_store_invalid`). If `LATEST` names a later run id and this
   run is not bound: `resume_superseded`; the message says the store can be deleted and names its
   project-relative path. A resume must not move `LATEST` back; DELIV's CAS also refuses at
   deliver, this says so before any work.
4. Build the current fingerprint; any run-level field different: `resume_fingerprint_changed`,
   naming the field (`config_hash`, `components`, `key_check`, `chunk_size`, `tables`), never a
   value. A table whose `binding_digest` differs: the same code, field `bindings`.
5. For each table with a valid activation record: the record's `artifact.path` must equal the
   current placed path of that table's target (else `bindings`); recompute the linked file's
   `sha256` and size, and the source's `sha256`. Call `plan_resume` (4.7).
6. Reopen the run: `RunLayout.open(..., run=RunFolder(path, run_id))` accepts an absent folder
   (recreated 0700), an empty one, or one already bound by this run (the K6 crash); open
   `DeliverySink` with the stored `operation_id`.
7. Kept tables: `sink.adopt_table(name, linked_file, artifact)` places the file into the new stage
   at the target's placed path through `durable_link_or_copy` (a copy is re-hashed) and records
   the table `ok`.
8. Rerun tables: the chunked loop of 4.4, writing new checkpoints.
9. Deliver as DELIV does. A crash after bind and before `LATEST` leaves the store in place; the
   next resume keeps every table, F22 judges the bound unit `already_committed` (equal
   `result_id`) and DELIV swaps `LATEST` (DELIV 7.1).

### 4.6 Locks

One `flock` on the store directory (`_folder_lock`, `src/decoy/_atomic.py:623`), taken by the
first attempt when it creates the store and by each resume after the delivered check, held until
the process ends. Order: store lock, then DELIV's pointer lock, then F22's run-id lock (DELIV 4.5
says F23 takes the same order). Nothing takes the store lock while it holds either of the others.

`_folder_lock` yields without locking when `fcntl` is missing (`_atomic.py:623-630`). Resume fails
closed there: on a platform without `fcntl` the first attempt writes no store and `--resume`
refuses `resume_platform_unsupported`. Windows resume is V2-LOG with F22 w1.

### 4.7 `plan_resume` (engine, pure)

Input: the stored and current fingerprints, the current table entries (index, name digest,
binding digest), and per table a `TableCheck(record_valid, artifact_ok, source_ok)`. Output:
`ResumePlan(keep, rerun, warnings)`, or `ResumeRefusedError(code, field)`.

| Case | Result |
|---|---|
| a run-level fingerprint field differs | refuse `resume_fingerprint_changed` |
| the table set or order differs from `RUN.json` | refuse `resume_fingerprint_changed` (`tables`) |
| a table's binding digest or placed path differs | refuse `resume_fingerprint_changed` (`bindings`) |
| record valid, artifact ok, source ok | keep |
| record valid, artifact missing or digest differs | rerun, warning `resume_checkpoint_invalid` |
| record valid, source changed or missing | refuse `resume_source_changed` (a kept table would come from another snapshot; rerunning only that table is a V2-LOG option) |
| no record, or record invalid | rerun |
| nothing to rerun | keep all, deliver (crash between the last record and bind or `LATEST`) |

The keep rule has no relationship closure: chunked tables are masked independently by
value-keyed strategies, so a kept parent and a rerun child agree on every key, as they do in an
uninterrupted chunked run (AT-R6 pins it).

### 4.8 Reason codes

Engine `reasons/decoy/_resume.py`, one `_catalog.decoy("DecoyResume")` family, each code with
`kind`, `severity`, `outcome` and `retry` as `reasons/decoy/_delivery.py` declares them, registry
minor by the renumber rule (roadmap 5.2 rule 1).

| Code | Kind | Severity | Outcome | Retry |
|---|---|---|---|---|
| `resume_run_dir_invalid`, `resume_layout_unsupported`, `resume_route_unsupported`, `resume_vault_unsupported`, `resume_platform_unsupported` | REFUSAL | ERROR | CONFIGURATION | NEVER |
| `resume_no_checkpoint`, `resume_store_invalid`, `resume_superseded`, `resume_fingerprint_changed`, `resume_source_changed` | REFUSAL | ERROR | CONFIGURATION | NEVER |
| `resume_in_progress` | REFUSAL | ERROR | CONFIGURATION | RETRY_OPERATION |
| `resume_checkpoint_invalid`, `resume_store_not_removed` | DECISION | WARNING | PUBLICATION | NEVER |

The enum member names follow `reasons/_types.py` on the merge head (E1 STEP ZERO maps each column
to an existing member; none is added). Refusals are category `usage`, exit 1. The CLI raises the
engine's `ResumeRefusedError(code, field=None)`; RESULT's `_errors.py` maps it through
`derive_outcome` like any usage error. No code string is copied into the CLI
(`tests/sentry/test_engine_reason_code_copies.py`).

### 4.9 Output and identity

- `--json` gains one member, `resume`: `{run_id, kept: [names], rerun: [names], invalid: [names]}`
  (names through `approve_name`), present only with `--resume`. Additive.
- The run summary gains one line: `resumed run <run-id>: kept 17 tables, ran 3`.
- `decoy-run-result/v1` is unchanged (RESULT's rule: no `_model.py` edit). Resume facts in the
  run-result document are a V2-LOG line.
- Identity: `mint_invocation_id` (`io/_layout.py:419-424`) promises that the run folder name, the
  evidence `run_id` and later run records carry one value. The delivered unit keeps that promise:
  a resume reuses the run id and passes the first attempt's `invocation_id` from `RUN.json` as the
  evidence `run_id` and the run-result id. The resume command still mints its own invocation id
  for what belongs to the process (notifications, telemetry spans, log lines), so each attempt is
  traceable. A list of attempts in the run result is V2-LOG.

### 4.10 Design notes

- New structure: one engine sub-package `delivery/resume/` (pure: fingerprint, codec, decision)
  and one CLI module `src/decoy/cli/io/_checkpoint.py` (the only writer and reader of the store),
  plus one helper in `src/decoy/_atomic.py`. Principle: one place per fact; the record shape lives
  once, in the engine, and the CLI never builds a record dict. Change pain addressed: platform
  resume later reads the same records and calls the same `plan_resume`.
- Choke point: every checkpoint write goes through `CheckpointStore.record_table`; every reuse
  goes through `CheckpointStore.verified_tables` and then `plan_resume`. Guard:
  `tests/sentry/run/test_one_checkpoint_store.py` walks the import graph and the syntax tree and
  fails when a module other than `io/_checkpoint.py` names a `decoy-resume-` tag or imports the
  `delivery.resume` record encoders. The existing `test_atomic_writer.py` keeps `os.link` inside
  `_atomic.py`. Mutation: write a record from `run/_execute.py` directly.
- House style: a typed `ResumeContext` on `RunContext`, not new parameters on `execute`; no flag
  argument switches the chunked loop (resume passes a `keep` set, empty on a first attempt).

## 5. Behaviour

| # | Case | Exit | Effect |
|---|---|---|---|
| B1 | first `--chunked` attempt succeeds | 0 | delivered; store removed |
| B2 | first attempt fails at table k (caught) | today's | stage aborted; store has records for tables 1 to k-1 (a masked copy on disk); resume hint printed |
| B3 | first attempt SIGKILLed | 137 (shell) | store as left; stage litter (F22 L2) |
| B4 | resume, all checks pass | 0 | tables 1 to k-1 kept (source read once to verify, not masked or written), k to n run, delivered in the same run id; store removed |
| B5 | resume, one kept file corrupted | 0 | that table reruns; warning `resume_checkpoint_invalid` |
| B6 | resume after a config, binding, component, key or chunk-size change | 1 | `resume_fingerprint_changed` naming the field; nothing written |
| B7 | resume after a kept table's source changed or went missing | 1 | `resume_source_changed`; nothing written |
| B8 | resume while the first attempt or another resume runs | 1 | `resume_in_progress` |
| B9 | resume after a later run delivered (this run not bound) | 1 | `resume_superseded`; the message says the store can be deleted |
| B10 | resume of a delivered run (bound, `LATEST` at it or later) | 0 | "already delivered"; any left store removed; nothing else written |

Existing fingerprints, and why `RunFingerprint` is separate:

- `PinnedEnvelope` (engine `generation/_reproducibility.py:150`) asserts generation
  reproducibility: `job_seed`, `config_digest`, `derive_key_digest`, custom providers, pinned
  inputs, locales, clock, `engine_minor`. It holds the job seed itself (secret-adjacent, so not
  for a file on disk), keys on the engine minor only, and has no source or target binding, no
  component versions and no chunk size. Resume reuses its idea (one value-free digest of every
  input) but cannot persist it.
- The evidence manifest fingerprints describe a delivered run after the fact; they are written at
  delivery, so they cannot key a store that must exist before the first table.

`RunFingerprint` is the pre-run, persisted, value-free key: masking semantics, bindings,
components, a key check and the chunk size.

- **OQ-1 (pending owner). The plain route.** `run_pipeline` returns every table at once, so a
  plain run has no finished table before it returns. Options: (a) V1 checkpoints the chunked
  route only; a plain run writes no store and `--resume` on it refuses `resume_route_unsupported`
  with "use --chunked for resumable runs"; (b) add a per-table output hook inside `run_pipeline`

  (a).** The long runs resume exists for are the chunked ones.

- **OQ-4 (go-recommended, coordinator 2026-11-13). Store retention.** A store never resumed stays

- **OQ-5 (go-recommended with M5, coordinator 2026-11-13). Resume of a run already delivered.**

## 12. Recurring-defect walk (`/home/cam/dev-rules/catalogs/recurring-defects.md`)

1. Anchored validation: digests, run ids and tags by `re.fullmatch`; AT-C2 has the `"\n"` cell.
2. Strict stored types: both records refuse `bool` and numeric strings (AT-C2).
3. No exception context: `ResumeRefusedError` is raised after the `except` closes; AT-R1 asserts
   `__cause__` and `__context__` are `None`.
4. Versioned read models: exact tag, missing tag refused, one writer model with the reader
   derived from it (as F22 a2).
5. Normalized guard scanners: the checkpoint sentry resolves `from ... import` aliases and
   re-exports of the record encoders; seeded cases per spelling; `os.link` stays with the
   existing `test_atomic_writer.py`.
6. No private imports: the CLI imports `decoy_engine.delivery.resume`, `decoy_engine.records`,
   `decoy_engine.keyprovider` and `decoy_engine.publication` public names only, and the layout
   helpers through the `decoy.cli.io` facade.
7. No hidden CI failures: no new CI job.
8. One trust class per entry point: `RUN_DIR` is user input and goes through the layout resolver;
   store file names are program names built from the validated leaf.
9. Mutations on the final head: recorded per slice.
10. Allowlisted helpers: the sentry allows `io/_checkpoint.py` by exact path; `durable_link_or_copy`
    callers are checked by `test_atomic_writer.py` by exact `(path, name)`.
11. No raised caps: `io/_layout.py` and `_atomic.py` must not need a cap change (stop line).

Value-free class (F31): records hold digests, counts, the name digest and the placed path; refusals
name fields; AT-V1 is the canary. Check then use: a kept file is re-hashed at reuse and placed by
the same path inside a 0700 store the user owns; a swap between hash and link is a named limit.

## 14. Pre-mortem

- DELIV slips and C1 waits for weeks. E1, E2 and C0 still land; the row's status names the wait.
  Do not wire checkpoints into today's pre-DELIV `_execute.py`: DELIV C2a rewrites that loop.
- The source digest pass doubles read time on slow disks. C1 measures it on the 10M fixture and
  records it; if it passes 15 percent of run time, raise it with the owner before C2b (V2-LOG has
  the in-read hash).
- A filesystem without hard links (some FUSE and exFAT mounts) makes every checkpoint a copy. The
  helper copies only on `_NO_HARD_LINKS` errnos; the cost is disk space, said in the guide.
- DELIV's merged sink names differ from `on_table_staged` and `adopt_table`, or F22 a3 names its
  measure differently. C1 STEP ZERO reads the merged code and uses its names; the names here stand
  for two capabilities (the staged path and measured artifact of a finished table, and placing a
  verified file into a new stage).
- F22 c1's restart rule changes before merge. C2b STEP ZERO re-reads F22 5.6 on the merged head;
  AT-K2f is the proof either way.
- A dependency outside `components` changes output bytes (for example a transitive Arrow or
  compression library). AT-R2 would show it in CI on an upgrade; the list grows by a reviewed
  change, not silently.
- `io/_layout.py` is near its 800-line cap. C2b adds only the `run=` parameter; the reopen logic
  lives in `_checkpoint.py`.
