# Phase 3.1: CLI native packaging default-on-when-present

Status: BUILT 2026-09-26 on `feat/cli-native-packaging-default-on`, pending dennis + Codex FINAL gate before merge (Codex PLAN gate GO 2026-09-24; 3 P2 build-time corrections folded below and applied during the build).
Risk: R2. Author: Opus.
Locked decisions (subject to the open questions below):
- Native-on-when-present is delivered by making the companion INSTALLABLE and PRESENT for CLI users and by inheriting the engine's existing default lane, not by adding a new native switch to the hot path.
- A companion that is `absent` is a clean Python fallback (portable-package contract). A companion that is PRESENT BUT NOT OK (abi-mismatch / kat-corrupt / load-error) is fail-closed by default, because it signals a broken install, not portable-package operation. This gate is a SHARED helper called from both `decoy run` and `decoy.mask()` before either writes output.
- `--native` means "require that a compiled kernel actually executed": it fails closed (writes no output) when the finished job carries no positive `compiled_kernel_executed` evidence, and refuses up front on an absent/broken companion. It is not a promise about companion health alone, because an ineligible or `--chunked` job finishes on Python even with a healthy companion.
- The route indicator reports THREE distinct states, not native-vs-pandas: (a) compiled-kernel native, (b) unified-slice-without-compiled-kernel, (c) legacy pandas adapter. A passthrough/redact/truncate-only job activates the unified slice WITHOUT the companion, so companion-absence does not imply the legacy pandas adapter ran.
- The CLI adds this three-state indicator, a `--no-native` rollback (`unified_slice_enabled=False`, legacy pandas adapter), and the `--native` require flag; it does NOT widen which shapes run native.
Roadmap: `decoy-platform/docs/ROADMAP.md`, execution-consolidation program, Stage B item 7 ("Phase 3.1: CLI native packaging default-on-when-present"). Governing program plan: `decoy-engine/docs/plans/2026-09-09-execution-consolidation-and-native-throughput.md` (Phase 3, §6.2 one preflight decision, §9.2 native companion states).

## FRAME

### Problem

CLI users cannot get the native speedup even when the machine could run it, and when the companion is half-installed they get the slow path with no signal.

Three concrete facts establish the gap:

1. **No install path for the companion.** `decoy`'s `pyproject.toml` declares only a `dev` extra (`optional-dependencies`, line 100-103); it exposes no user-facing extras and never pulls in the compiled companion `decoy-engine-native`. The engine likewise declares no `native` extra yet, and its `pyproject.toml` (lines 313-329) records exactly why: the companion is unpublished (no PyPI release, no version), so a bare `native = ["decoy-engine-native"]` desyncs the lock; the extra "lands with the first paired PyPI release, pinned exactly, per the ABI-tag compatibility contract." So a plain `pip install decoy-cli` user never has the companion, and `native_companion_status()` reports `absent` with the message "no 'native' extra exists yet; install it directly" (`_companion_status.py::_absent_status`). The native lane is unreachable for CLI users purely for packaging reasons.

2. **The engine already does native-on-when-present, silently.** `decoy run` (non-chunked) calls `decoy_engine.run_pipeline(...)` at `src/decoy/cli/run.py:523` without passing `unified_slice_enabled`, so it inherits the engine default `True` (flipped from `False` on 2026-09-20, `_pipeline.py:172`, per `docs/plans/2026-09-20-unified-slice-activation.md`). `run_pipeline` calls `maybe_run_unified_slice` (`execution/_unified_slice.py`), whose admission (`_unified_slice_admission.py`) gates a hash column on the companion probe: `if hash_columns and not native_companion_status().ok: return None` (line 408). When the companion is present-ok, an admitted hash node MUST show `compiled_kernel_executed` evidence or the run fails closed (`_unified_slice.py:279-286`); when it is not ok, admission returns `None` and `run_pipeline` reroutes to the pandas full-frame oracle. `decoy.mask()` (`src/decoy/api.py:431`) does the same. So the engine mechanism is built and default-on; the CLI just never has a healthy companion to trigger it and never tells the user what happened.

3. **No visibility, and a silent-degradation trap.** Nothing in the CLI surfaces the native path. `info.py`, `preflight.py`, and the `decoy run` summary have no companion/native/route awareness (grep: zero hits for `native`/`companion` in those handlers beyond unrelated text). Worse, a PRESENT-BUT-BROKEN companion (`reason` in `abi-mismatch` / `kat-corrupt` / `load-error`) makes `native_companion_status().ok` False, so admission declines and the job runs pandas with no warning. A user who deliberately installed the native extra silently gets the slow path, which is exactly the "does not silently accept degraded throughput" hazard the program governance calls out (§9.2).

### Definition of done

- A CLI user can install the companion through the tool they install (`decoy-cli[native]`, or a documented direct-install path while no paired PyPI release exists), pinned to an ABI-compatible companion version.
- With a healthy companion present, an eligible `decoy run` / `decoy.mask()` job runs the compiled kernel with no new flag; with the companion absent an eligible hash job runs the Python (pandas) path; the masked cell values and Arrow schema are identical either way (the engine's D9 contract), and the CLI's own written output file bytes are identical for a fixed writer.
- The user can see which of the three route states ran (a run-summary line) and can query companion health ahead of time (`decoy info`, `decoy preflight`).
- A present-but-broken companion fails closed (via the shared gate) with a coded reason and remediation, rather than silently degrading; `--no-native` downgrades that to a fallback for rollback; `--native` requires positive compiled-kernel evidence and fails closed (no output written) otherwise.
- The config contract is unchanged (no `PipelineConfig` field); the hot path and masked output are unchanged when the companion is absent.

### Boundaries

- Change CLI packaging (extras), CLI dispatch plumbing, and CLI surfacing only. Do NOT change engine masking logic, the unified-slice admission predicate, the companion probe, or any kernel. Those are built, reviewed, and D9-certified (engine #164).
- Scope the native lane to what the engine admits TODAY: a single non-FK, resident (in-memory) mask table over exactly `passthrough` / `redact` / `truncate` / `hash` (the `ALLOWED_OPERATOR_IDS` allowlist, `_unified_slice_admission.py:78`). Multi-table, FK, out-of-core, deterministic-faker, and other strategies continue on their existing routes regardless of the companion. Phase 3.1 does not widen native coverage.
- `--chunked` (`_run_chunked_mask` -> `run_mask_pipeline_chunked`, `run.py:892`) stays on the pandas oracle. The native chunked coordinator (`run_native_or_oracle_chunked` via `physical/drivers/_chunked.py::ChunkedDriver`) is Phase 4 Task 4.6 work and is dormant; wiring it is out of scope here.
- No platform work. Phase 3.2 (companion bundled in the production image with a fail-closed worker gate, engine #135 / platform #45) already covers the platform; this plan is the CLI distribution.

### Applicable rulebooks

`feature-dev`, `packaging` (a new optional-dependency extra and a version/ABI pin), `api-and-compatibility` (a public behavioral change: the default install can now run native; new CLI flags), `testing`, `verification`, `security` (the route indicator and status output must not print source values, keys, or `status.cause` secrets). CLI `CLAUDE.md`: the CLI is a thin wrapper; all data logic stays in the engine, so this plan adds no masking code CLI-side. Established-methodology: reuse the engine's `native_companion_status()` probe and `docs/native/supported-matrix.md`; do not re-implement companion detection in the CLI.

### Risk

R2: changes a packaging/compatibility contract and, once the companion is installable, changes the default execution path and (for a broken companion) the job outcome. Cryptographic determinism is unchanged (the kernel is byte-parity-certified), but a packaging or fail-open mistake would either mislead users about which path ran or ship an unrunnable install. No author self-certification; written plan + independent plan review before implementation; adversarial review (dennis) + Codex final gate + exact-artifact gate before merge.

## Approach

The engine lane exists and is default-on. Phase 3.1 makes it reachable, visible, and honest for CLI users, in four parts.

1. **Packaging: a `native` extra, ABI-pinned, with a documented interim path.**
   Add `native` to `[project.optional-dependencies]` in `decoy/pyproject.toml`. Its content is gated on the paired release the engine pyproject documents (lines 321-329): the companion `decoy-engine-native` must be published and versioned before a lock-resolvable extra can exist.
   - Preferred once the engine ships its own `native` extra: `native = ["decoy-engine[native]>=<pinned>"]` so the CLI (distribution `decoy-cli`, so the user types `pip install decoy-cli[native]`) forwards to a single engine-owned pin. The engine extra pins its OWN companion against its own version, so the ABI rule lives in one place and the companion cannot pair with a different-ABI engine.
   - If the engine has not yet added its extra at build time, pinning the companion directly is NOT sufficient on its own: the CLI's base dependency is open-ended (`decoy-engine>=0.5.0`, `pyproject.toml:94`), so `native = ["decoy-engine-native==<version>"]` alone still permits pip to resolve a newer, different-ABI engine beside a pinned companion. A direct pin must therefore ALSO constrain the compatible engine range in the same extra (`native = ["decoy-engine-native==<version>", "decoy-engine>=<lo>,<<hi>"]`) matching the ABI tag `decoy-native-abi-2` (`_EXPECTED_ABI_VERSION`, `_crypto_ext.py:358`) per `docs/native/supported-matrix.md`'s core-to-companion rule, plus a `[tool.uv.sources]`/workspace entry so `uv.lock` stays resolvable. The runtime ABI/KAT probe still catches a bad pair at load time and is the ultimate safety gate, but it is a runtime backstop, not a substitute for a resolver-level constraint: the pin's job is to stop pip choosing a skewed pair in the first place.
   - While no PyPI release of the companion exists at all (the self-hosted single-org reality today), the extra cannot be created without desyncing the lock. In that window, ship a documented direct-install path only (a wheel or index URL in the CLI README / `decoy explain native`), and land the extra in the same change as, or immediately after, the first paired release. The runtime probe is the real safety gate regardless of how the companion arrived, so a hand-installed companion is fully supported.

2. **Dispatch: inherit the engine default, add a rollback and a require flag.**
   Non-chunked `decoy run` already inherits `unified_slice_enabled=True`, so native-on-when-present needs no change to the happy path. Add a `--native/--no-native` option (default: neither; inherit engine behavior) to `decoy run`, and the equivalent `native: bool | None = None` argument to `decoy.mask()`:
   - `--no-native`: pass `unified_slice_enabled=False` to `run_pipeline`, forcing the legacy pandas full-frame adapter. This is the documented rollback and the way to reproduce the pre-native path on demand.
   - `--native` (require compiled-kernel execution): the honest promise is "a compiled kernel actually ran", not "the companion is healthy". A healthy companion does NOT guarantee native execution: an ineligible shape finishes on Python regardless. `--native` is enforced in three stages, ordered so nothing writes before the guarantee can be honored:
     - Stage 0 (reject BEFORE dispatch, no run): if the invocation is not even a unified-slice candidate, it is a usage error and the job never runs. This covers `--native --chunked` (the chunked path at `run.py:518` streams output per chunk through `_write_chunked_output`, so a run-then-check would already have written partial output — it must be rejected before dispatch, not after), and `--native` on a generate-only or mixed config (`any_generate`, `run.py:484`), which never routes through the unified slice and so could never show compiled-kernel evidence. These exit with a coded usage error explaining native applies only to a non-chunked, mask-only run.
     - Stage 1 (up-front companion health): a fast `native_companion_status()` check refuses an absent/broken companion before any compute, with a coded usage error naming the `reason` and remediation.
     - Stage 2 (post-run evidence, non-chunked mask path only): after `run_pipeline` returns and BEFORE `_write_mask_outputs` (`run.py:531`, which is the FIRST write on this path — the non-chunked route buffers outputs in memory), assert positive `compiled_kernel_executed` evidence for the hash node(s) in `result.quality_metrics["unified_slice_activation"].nodes`; if the job finished without a compiled kernel (a candidate that turned out runtime-ineligible: non-Parquet source, FK/relationships, validators/quarantine, or the unified-slice-without-kernel state), fail closed and write NO output, with a coded error explaining the shape ran on Python. Stage 2 is safe precisely because this path writes nothing until after the check; it costs a full run before the refusal, acceptable single-org.
   - No flag: inherit today's behavior (compiled-kernel native when the shape is eligible and the companion is present-ok; otherwise the unified-slice-without-kernel path or the legacy pandas adapter, per the shape).
   Do not add a `native_route_enabled` parameter to `run_pipeline`; the engine's native decision is `unified_slice_enabled` plus the admission probe, and this plan keeps that seam intact.

3. **Fail-closed on a broken companion, shared between the CLI and the library (governance §6.2 / §9.2).**
   `decoy.mask()` (`api.py:431`) calls `run_pipeline` independently of `decoy run`, so a gate that lived only in `run.py` would leave the library's silent fallback intact and a `native=` argument there would be cosmetic. Put the policy in ONE shared module (`decoy/_native_gate.py` in the CLI package, reusing the engine's `native_companion_status()`), exposing TWO functions that both `decoy run` and `decoy.mask()` call:
   - a PRE-EXECUTION gate, taking the resolved native intent (default / `--native` / `--no-native`, or the `mask(native=...)` argument) and the probe status, applied before the engine call (Stage 0/1 of approach 2, and the broken-companion classification below);
   - a POST-RUN result verifier, taking the `ExecutionResult` and the intent, applied before EITHER write point — the CLI's `_write_mask_outputs` (`run.py:531`) AND `mask()`'s own return/write (`api.py:440`) — that, when native was required, asserts positive `compiled_kernel_executed` evidence and fails closed (no output written, no DataFrame returned) otherwise. Specifying it as a shared step is what stops `mask(native=True)` from silently writing an ineligible-shape result the CLI would refuse.

   The pre-execution gate classifies the probe states whenever a mask job could be native-eligible:
   - `absent`: clean Python fallback. Emit one informational line (suppressed in `--quiet`/JSON-quiet) stating native is not installed and how to add it. Exit 0. This is the portable-package contract (§9.2: "the portable Python package can run without the companion ... uses the approved fallback").
   - `present-ok`: proceed silently; the run-summary indicator reports the actual path.
   - `abi-mismatch` / `kat-corrupt` / `load-error` (present but not ok): fail closed by default with a coded error carrying `reason`, `abi_expected`, `abi_actual`, and remediation (reinstall the matching companion, or run `--no-native`). Never print `status.cause` verbatim (it may chain an exception with a path); print the classified `reason` only. `--no-native` turns this into a warned fallback for rollback. This is the "fail-closed when a native op is requested but unavailable" requirement, applied to the case that actually risks silent degradation.
   Rationale for making broken (not absent) the fail-closed case: absence is normal portable operation; a present-but-broken companion is a deployment defect and mirrors the platform worker's own fail-closed startup gate (Phase 3.2). The default is a product call (open question 1).

4. **Surface which route ran (governance §6.6 observable routing), scoped to where the unified slice is even a candidate.**
   The three-state native indicator applies ONLY to a unified-slice CANDIDATE run: a non-chunked, mask-only (no `any_generate` table), full-frame job. `decoy run` also accepts generate-only and mixed configs (`run.py:484`), and the unified-slice admission declines any non-full-frame route (`_unified_slice_admission.py:142`), so a MISSING `unified_slice_activation` key on those jobs does not mean the legacy pandas adapter ran. The indicator therefore first classifies the run, then reports:
   - Unified-slice candidate (non-chunked mask-only full-frame): read `result.quality_metrics.get("unified_slice_activation")` (`QUALITY_METRICS_KEY`, `_unified_slice.py:68`). (a) key present, `activated`, any node `compiled_kernel_executed=True` (the hash operator `native_keyed_hash`, `HASH_OPERATOR_ID`): `Route: native (compiled kernel)`. (b) key present and `activated`, every node `compiled_kernel_executed` false: `Route: unified slice (no compiled kernel)` — the coordinator ran a passthrough/redact/truncate-only job WITHOUT the companion, so this is NOT the legacy pandas adapter and must not be labeled "pandas". (c) key absent on a candidate: `Route: pandas (legacy adapter)` — the candidate fell through to the legacy full-frame route (e.g. companion absent for a hash job, or a runtime-ineligible shape).
   - NOT a unified-slice candidate (generate-only, mixed, `--chunked`, or otherwise non-full-frame): the native indicator is not applicable. Report the actual route those paths expose — for `--chunked`, `Route: pandas chunked stream`; for a generate/mixed/out-of-core run, the engine's own route telemetry (`quality_metrics["execution"]`, the `execution_mode` field surfaced by `_pipeline_route_exec.execution_telemetry`, `_pipeline_route_exec.py:81`) — or a neutral `Route: n/a (not a unified-slice candidate)` when no finer route label is exposed. This is classified SEPARATELY from compiled-kernel evidence and never infers legacy-pandas from a missing activation key on a job that never routes through the slice.
   Include the state and its scope in the JSON run record.
   - `decoy info`: add companion presence, `reason`, `abi_expected`, a sanitized `abi_actual`, and `version` from `native_companion_status()` (JSON and human modes); never `status.cause`.
   - `decoy preflight`: add a companion-health check (pass/warn/fail from `native_companion_status()`) and a clearly LABELED STATIC possibility line for THIS config, e.g. `Native eligibility: eligible by config (single non-FK Parquet mask table, native strategies); actual route depends on the resolved profile and resident data at run time`. A truthful "would run native" cannot be established at preflight: real admission needs the resolved route, the source profile, the resident Arrow table, and the compiled physical plan plus data-dependent checks (`cheap_admission` inputs, `_unified_slice_admission.py:123`; `resident_contract_admission`, `:314`), none of which preflight's profile-free config checks have. So the preflight line reuses only the config-shape half of the predicate (single table, non-FK, Parquet file source, native-eligible strategies, no validators/quarantine/storm/vault/fidelity) and is explicitly labeled a static possibility, not a guarantee. Designing a full read/profile/compile dry path is out of scope (it would duplicate the run cost); recorded as open question 5.

## Observable behavior

1. Companion present-ok, eligible hash job (single non-FK resident Parquet table): the compiled kernel runs; the summary reports state (a) `native (compiled kernel)`; `quality_metrics["unified_slice_activation"].nodes[hash].compiled_kernel_executed` is True.
2. Companion absent, eligible hash job: the legacy pandas adapter runs (admission declines on `not ok`); the summary reports state (c) `pandas (legacy adapter)`; one informational line names the missing `decoy-cli[native]` extra; exit 0; masked cells + Arrow schema identical to (1).
3. Companion absent (or present), eligible NON-hash job (passthrough/redact/truncate only): the unified slice activates WITHOUT the companion; the summary reports state (b) `unified slice (no compiled kernel)`, never "pandas".
4. Companion present but abi-mismatch / kat-corrupt / load-error, no flag: the shared gate refuses with a coded error and remediation; no masked output is written; the classified `reason` is shown, `status.cause` is not.
5. Same broken state with `--no-native`: warned fallback to the legacy pandas adapter; exit 0.
6. `--native` with an absent or broken companion: usage-level refusal before any work; the `reason` is named.
7. `--native --chunked`, or `--native` on a generate-only/mixed config: rejected BEFORE dispatch as a usage error (Stage 0). The job never runs and nothing is written (the chunked path would otherwise stream partial output). The message says native applies only to a non-chunked, mask-only run.
8. `--native` with a healthy companion on a non-chunked mask-only candidate that turns out runtime-ineligible (non-Parquet source, FK/relationships, validators/quarantine): the job runs, then fails closed BEFORE the single write at `run.py:531` because no `compiled_kernel_executed` evidence is present; a coded error explains it ran on Python. No false native claim, no output file (safe because this path buffers and writes only after the check).
9. No flag, native-ineligible or non-candidate shape with a healthy companion: runs its existing route; the indicator reports state (b)/(c) for a candidate, or the actual non-candidate route / `n/a` otherwise; exit 0.
10. `decoy info` reports companion health; `decoy preflight` reports companion health plus a clearly labeled static native-eligibility possibility for the given config, without running the job.
11. `decoy.mask(native=...)` mirrors the CLI: the same shared pre-execution gate and post-run result verifier govern it, so the library cannot silently write an ineligible-shape result the CLI would refuse.

## Byte-parity requirement

Two distinct claims, kept separate:

1. Masking CORRECTNESS across routes is the engine's, not this plan's. The D9 certification proves the unified-slice lane produces matching output CELLS and matching Arrow schema metadata versus the pandas full-frame route (Task 4.5; source-shaped reconstruction attaching the identical `b"pandas"` schema metadata by construction, `_unified_slice.py:293-317`), and the keyed-hash kernel is KAT- and differential-parity-proven (Phase 1). It does NOT assert identical serialized file bytes; that is not what D9 measures. Phase 3.1 adds no masking code, so it inherits this and re-asserts it only as a guard against a dispatch regression that silently swapped routes.
2. Output FILE bytes are the CLI's own contract, because the user consumes a written file. `_write_mask_outputs` is the fixed CLI writer for a given format, so for a fixed writer and format the written file must be byte-identical whether the run took state (a), (b), or (c). The CLI acceptance suite tests the written-file bytes directly (companion present vs absent vs `--no-native`), rather than leaning on the engine cell/schema cert to imply file-byte equality.

## Known failure modes

- **Version skew between the CLI/engine and the companion.** A companion built for a different ABI, or a stale companion predating the index kernel (a valid abi-2 hash-only build that lacks `derive_index_batch`), reports `abi-mismatch` or `load-error`/incomplete. The probe classifies both (`_companion_status.py` checks BOTH crypto and index KATs), so the CLI's fail-closed/rollback handling (approach 3) catches a bad pair at load time. Note the extra's pin does not by itself prevent skew: with the CLI's open-ended `decoy-engine>=0.5.0` base dep, a companion pin alone still lets pip pair it with a different-ABI engine, which is why approach 1 forwards to a paired `decoy-engine[native]` extra or, for a direct pin, also constrains the engine range. The pin reduces the chance of a skewed resolve; the runtime probe is the guarantee.
- **Unsanitized ABI string in output.** `abi_actual` comes from the companion's own `abi_version()` call (`_companion_status.py:255`), i.e. from an installed third-party artifact, so it is untrusted for display. Bound and sanitize it (length cap, printable-only) before showing it in `decoy info` / `decoy preflight` / an error, and continue to exclude `status.cause` entirely.
- **Partial install.** A companion importable but failing its KAT (`kat-corrupt`) or missing a symbol (`load-error`) is the present-but-not-ok trap; handled by approach 3, not silently downgraded.
- **Lock desync.** Declaring the extra before the companion is published breaks `uv sync --frozen` (the exact hazard the engine pyproject documents). Mitigated by gating the extra on the paired release and shipping only a documented direct-install path in the interim.
- **False native claim.** A summary that read intent (the flag) rather than evidence would mislabel a rerouted job. Mitigated by reading `compiled_kernel_executed` evidence, never the flag (governance §6.6).
- **Secret/PII leakage in output.** The route indicator and `decoy info`/`preflight` must print only counts, codes, ABI tags, and versions, never source values, keys, or `status.cause` contents. Covered by a privacy test.
- **Install-size expectation.** Pulling the companion adds to an already ~600-650 MB install (`docs/plans/2026-08-26-cli-install-dx-extras.md`); keep it opt-in via the extra, never a hard dependency, consistent with the lean-default DX direction.

## Open questions (for the plan-gate and Cam)

1. **Broken-companion default: fail-closed or warned-fallback? (product call, Cam.)** Recommendation: fail closed by default (a present-but-broken companion is a deployment defect, and silent degradation is the governance hazard), with `--no-native` as the explicit downgrade. The alternative (warn + fall back by default) is friendlier but risks a user believing they run native when they do not. Cam decides the default; the mechanism supports either.
2. **Packaging trigger.** Confirm the companion will be published (PyPI or a self-hosted index) so a lock-resolvable `native` extra can exist, versus staying a direct-install-only artifact for the self-hosted single-org product. If the latter, Phase 3.1 ships the surfacing + fail-closed + flags now and documents the direct install, and the extra is deferred to the release. Recommendation: ship everything except the extra now; land the extra with the first paired release.
3. **Extra shape.** Prefer forwarding `decoy-cli[native]` -> `decoy-engine[native]` (one owner for the ABI pin) once the engine adds its extra, versus the CLI pinning `decoy-engine-native` directly. Recommendation: forward to the engine extra to keep the version/ABI rule single-sourced in `docs/native/supported-matrix.md`.
4. **Should `--no-native` also disable the non-hash unified-slice lane?** `unified_slice_enabled=False` reverts the whole lane (including the coordinator-owned redact/truncate/passthrough path, which does not need the companion). That is the cleanest rollback and reproduces the legacy path, so recommendation: yes, `--no-native` maps to `unified_slice_enabled=False` wholesale. Confirm no eligible non-hash job loses a wanted behavior by reverting.
5. **Preflight native-eligibility: labeled static possibility, or a full dry path?** Recommendation (adopted in approach 4): a clearly labeled static possibility from the config shape only, because a truthful "would run native" needs the resolved route + profile + resident Arrow table + compiled physical plan + data-dependent checks (`_unified_slice_admission.py:123`/`:314`), which a full read/profile/compile dry path could produce only at roughly the cost of the run itself. Confirm the labeled-static line is acceptable, versus funding the dry path.

## Build corrections (dennis + Codex adversarial gate, 2026-09-26): applied post-build

Two rounds of adversarial review (dennis, Codex) after the initial build found this plan's own facts had drifted between the PLAN gate (2026-09-24) and the build (2026-09-26), plus gaps the build introduced. Corrections actually applied to the shipped code (see `src/decoy/_native_gate.py` and its tests for the current, authoritative behavior):

1. **Correction #3 above was itself stale by the time the build ran.** Engine main's `ALLOWED_OPERATOR_IDS` grew to seven operators (`native_categorical` / `native_bucket_perturb` / `native_group_key` landed on engine main before this plan's own PLAN-gate date) -- the "exactly four" fact this plan asserted was already wrong when written. The shipped code tracks the engine's actual admitted set (`_NATIVE_STRATEGIES`) and its companion-dependent subset (`_COMPANION_DEPENDENT_STRATEGIES` = hash/categorical/bucket_perturb/group_key), not a hardcoded four. Definition-of-done line 38 and the acceptance-test wording elsewhere in this doc that assume "hash column" specifically are superseded by "a companion-dependent-strategy column."
2. **No install path exists, not even a direct one.** This plan's Definition of Done and approach 1 assumed a documented direct-install path (a wheel/index URL) would exist for the interim. It does not: `decoy-engine/docs/native/supported-matrix.md` documents the companion's CI build pipeline, not a place a user can `pip install` or download from. The shipped messaging (info hints, `decoy explain native`, `--native`'s remediation text) says this honestly instead of naming `decoy-cli[native]` or that doc as if either works today.
3. **Output-file-byte parity for state (a) vs (c) needed an actual compiled companion**, not just a mocked `quality_metrics` shape, to be real acceptance evidence. One was built locally (`maturin develop --release` in `decoy-engine/decoy-engine-native`) and the test suite uses it when present (`tests/e2e/test_run_native.py::test_run_native_when_companion_present_ok` and the byte-parity test next to it), skipping gracefully when absent (e.g. in CI, which does not build one). A portable, no-companion-required version of the same tests (mocking `run_pipeline` to real-compute then relabel) remains as a regression net under it.
4. **The static eligibility predicate needed to match a growing part of `cheap_admission`'s config-visible declines**, not just `validators`: added quarantine, `run_storm`, table-level `transforms`, a per-column `when:` gate, a live vault writer (both the config-shape `vault: true` marker and the caller's actual runtime writer state), an exact resident-source-set check (`{table}`, no extras), an exact `format == "parquet"` match (no path-suffix inference, which could wrongly admit a mislabeled `format: csv` source with a `.parquet`-named path), and a categorical-determinism check (`deterministic`/`allow_collisions`, mirroring `is_deterministic_categorical`) since a plain `strategy: categorical` column defaults to the random, non-native path. This is a CONFIG-VISIBLE SUBSET of `cheap_admission`, not an exact match -- it still cannot see resident types, schema equality against the source, or group_key sibling admissibility, all of which need the resolved profile this predicate does not have. The engine's own config-only equivalent, `native_route_eligibility` (`decoy_engine.execution.native._plan`), would close this gap precisely, but it is not exported at the engine's public boundary; using it would mean reaching into a private engine module, which is a bigger call than this round's time budget covers -- tracked as a follow-up, not silently dropped.
5. **Companion-health gating stays all-or-nothing (the engine's public `native_companion_status().ok`), not per-kernel** (`native_kernel_availability()`, which exists only in the engine's private `execution.native._companion_status` module). This is documented in `_native_gate.py`'s module docstring as an accepted, over-conservative gap: a companion missing only an additive kernel (e.g. raw-hex) is treated as fully broken here even though the engine would still run hash/categorical/bucket_perturb natively. Closing this properly needs the engine to re-export `native_kernel_availability()` publicly -- an engine-repo follow-up, not a CLI-side fix.
