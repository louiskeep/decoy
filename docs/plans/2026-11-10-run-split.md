Base: CLI `origin/main` `4b47b66`. Every line number below is on that commit, where

(`38cdb69`) and CLI #176 (`40f464b`) are already in this base. Section 4 includes #174's

## 1. Why, and what this row does not do

Roadmap section 5.2 rule 2 lets only one branch at a time write `run.py`, so the 14 rows that
touch it build one after another. Most of them change different parts of the command: the
error-to-exit mapping, the execution route, the summary, the evidence file, notifications. The
split puts each part in its own module so those rows can build in parallel lanes, one writer
per module.

This row closes no roadmap row and changes no product behavior. Same exception classes, exit
codes, non-verbose output bytes, JSON, `--help`, lazy-import behavior and order of side effects.
Verbose tracebacks necessarily name the new file and phase frame instead of `run.py::run`; that
structural, server-admin diagnostic change is V2-LOG and is the only allowed output difference.
It changes no reason text, error text, baseline entry, baseline count or existing test assertion.
It pays down no debt beyond what the move needs: anything better done later is listed under
"Follow-ups", not done here.

## 2. Target layout

`src/decoy/cli/` is frozen to new modules (CODEMAP "Where things go": "`cli/` is frozen"), and
it already holds 32 flat modules, past the 25 limit. Turning `run.py` into the package
`run/` adds no flat module (32 becomes 31 files plus one package) and keeps the import path
`decoy.cli.run` working, so `__main__.py`, `api.py` and `tokenize.py` need no import edit.

Why `run/` rather than the `scan.py` plus `scanning/` shape: `scan.py` kept its options and
moved the internals to a sibling package. For `run` that would leave `run.py` as a 350-line
options file next to a `running/` package, and every site key that names `cli/run.py` would
still move. The package keeps one name and one place. A module `run.py` cannot sit beside a
package `run/` (the package shadows it), so the split deletes `run.py` in the same commit.

All imports inside the package are absolute (`ban-relative-imports = "all"`; the AST sentries
resolve absolute imports only).

Changes from the task's proposed list, by reason:

- No `_generate.py`. `run.py` has no generate route: generate and mask both go through the one
  `run_pipeline` call. The generate-only pieces are the key resolver (pre-run, so
  `_prepare.py`), the chunked-generate refusal (`_execute.py`, with the other chunked
  refusals) and #176's `uniqueness_impossible` exit (`_errors.py`). A `_generate.py` would be
  a 40-line module with no row that writes only it.
- `_mask.py` is named `_execute.py`, because its plain branch runs generate too.
- `_render.py` is split from `_evidence.py`: RESULT and F29 C1 write the summary, L3a writes
  the evidence and run records. Same file would put them back in one lane.
- `_flow.py` and `_context.py` are new. Without them, `run()` stays a 1,000-line function in
  some module, and the thin `__init__.py` goal fails.
- Each error class lives with the code that raises it, and `_errors.py` imports them. That
  keeps the import graph acyclic: `_context` (no sibling imports), then `_notify`, `_vault`,
  `_execute`, then `_prepare`, then `_errors`, `_render`, `_evidence`, then `_flow`, then
  `__init__`. A module imports only modules earlier in that order.

## 3. How `run()` is cut

Moving the top-level helpers is a plain move. `run()` is not: its body is one function of
about 760 lines, and its locals cross from one phase to the next. Two rules keep the cut
mechanical. In Fowler's terms the row performs: Move Function and Move Field for the top-level
definitions (rule M1), Introduce Parameter Object (`RunContext`) and Extract Function for the
phases of `run()` (rule M2). Each step's commit names its refactoring.

**Rule M1 (top-level defs).** A module-level class, function or constant moves with its body
byte for byte. Only import lines change. A name another module needs is imported from the
module that now defines it.

**Rule M2 (`run()` phases).** The body of `run()` is cut at the phase boundaries in the
Placement table. Each phase becomes one function taking `ctx: RunContext` (plus `_scopes`
where the phase enters a context). Inside a phase the statements stay in order and verbatim,
with exactly two allowed edits:

1. A name on the shared-state list below is read and written as `ctx.<name>`. The field name
   equals the old local name, leading underscore included, so the review check is a pure
   prefix. Renaming the fields is a follow-up.
2. A name bound by the two lazy engine imports (`run_pipeline`, `engine_version`) is assigned
   to the same-named `ctx` field immediately after the original import, at current line 601,
   and the later phase reads that field. The import is neither moved nor repeated. This keeps
   import failure timing, monkeypatch lookup timing and the help path unchanged, and it avoids
   an unused import in `_prepare.py`.

No other statement changes. No condition is merged, no helper is introduced, no comment is
reworded. A comment that sits on a moved statement moves with it. The `RunContext` field
declarations are new scaffolding outside the extracted phase bodies, not a third permitted
body edit.

`RunContext` is a `@dataclass(slots=True)` (Python 3.10 is the floor). Slots make a misspelled
`ctx._ev_timngs = ...` raise `AttributeError` instead of quietly adding an attribute. Each
sentinel's default and its comment move from lines 561 to 589 onto the field. The two clock
reads (`_run_started_at` at line 591, `started` at 592) stay statements in `_flow.execute` at
the same point in the order, not dataclass defaults, so the start time is taken where it is
today.
Scalar, tuple and `None` sentinels keep the same value. A list or dict sentinel uses
`field(default_factory=...)`, and an acceptance cell invokes `run` twice to prove that mutable
state is not shared. Computed flags remain assignments in `_flow.execute`; they are not
dataclass defaults. The comparison oracle has a separate row-by-row mapping from lines 561-589
to these fields and refuses an omitted field, changed type or changed default.
`run_pipeline` and `engine_version` are `field(init=False)` bindings, so constructing the
context does not create a value or import the engine; `_prepare.prepare` assigns them exactly
where the current lazy imports run, before any pre-check statement.

Shared-state list (fields of `RunContext`):

- the 24 options: `config`, `mode`, `json_`, `quiet`, `verbose`, `master_key`, `mask_secret`,
  `chunked`, `chunk_size`, `max_memory`, `threads`, `vault`, `key_label`, `evidence_out`,
  `notify`, `notify_on`, `native`, `no_native`, `explain_plan`, `fidelity`, `post_validate`,
  `post_validate_enforce`, `duckdb_source`, `otel_endpoint`;
- set before the try: `state`, `config_str`, `notify_channels`, `raw`, `saved_findings`,
  `config_read_error`, `raw_cfg`, `yaml_mode`, `resolver`, `post_validation`, `_report_flags`,
  `_run_started_at`, `started`;
- the sentinels: `_duckdb_tmpdir`, `_ev_config_dict`, `_ev_engine_version`, `_ev_row_counts`,
  `_ev_timings`, `_ev_engine_warnings`, `_notify_row_count`, `_table_records`,
  `_native_route`, `_resources_record`, `_report_quality_metrics`;
- set in `_prepare` and read in `_execute`: `config_dict`, `gate_result`, `any_generate`,
  `native_intent`, `_res`, `sources`, `key_provider`, `_key_kwargs`, `vault_writer`,
  `run_pipeline`, `engine_version`;
- set in the success tail and read by `_render`: `elapsed`, `notify_results`.

The list is from reading the code. Before moving anything, the builder runs a throwaway AST
script over `run()` that reports every name assigned in one phase span and loaded in another,
and adds anything it finds to the list in the PR body. A name used in one phase only stays a
local.

The rename touches names only, never strings or comments: `"mode": yaml_mode` becomes
`"mode": ctx.yaml_mode`, and `state.mode` is untouched. An f-string's expression part is
renamed (`f"Running {ctx.yaml_mode}..."`); each such line is listed in the PR body.

The except arm keeps today's exception context. `_flow.execute` calls
`_errors.fail(ctx, exc)` inside `except Exception as exc:`, and `fail` ends with
`raise typer.Exit(code=_exit_code)` as line 1163 does. Raised inside the except block, the
exit carries the same `__context__`, and `print_traceback(state)` still sees the active
exception. Calling `fail` after the except block closes would change both, so the plan rules it
out. (Recurring-defect 3 asks new code to raise after the block; this is moved code and keeps
today's behavior. See Follow-ups.)

The function boundaries do not move statements across a control boundary. `_prepare.prepare`
and `_execute.execute` are called, in that order, inside the same spinner and `ExitStack`; their
exceptions reach the same `except typer.Exit`, catch-all and `finally`. Evidence, success
notification and `_render.finish` remain after the `finally`, and `_render.finish` is the final
call in `_flow.execute`, so its JSON and quiet `return` statements are still terminal. The
engine `__version__` and `run_pipeline` bindings cross the phase through `ctx`; their single
lazy imports stay at the current pre-check point. All other lazy imports, including
`_seed_warnings`' reason-code import, move with their statement. A package-shape sentry rejects
any module-level `decoy_engine` import, which keeps
`decoy run --help` on the same import path. These constraints preserve exception classes, exit
mapping, output order and lazy-import behavior; the exact tests are in section 6.

### 5.3 Baseline moves: settled option A, first commit of this PR

`scripts/dev/ratchet_check.py` runs first in the gate's sentry step and fails when a registered
baseline gains a key not in the merge base. It has no notion of a rename. The split renames
three keys in `private-file-sinks.json` and one in `atomic-writer-allow.json`, so the gate
fails with "baseline gained key(s) not in the merge base", although nothing was added.
`test_ratchet_check.py:116` (`test_renamed_baseline_with_extra_key_fails`) shows the strictness
is deliberate.

The owner chose option A. The first commit of this same RUN-SPLIT PR teaches
`scripts/dev/ratchet_check.py`, through its one shared implementation in
`tests/sentry/_ratchet.py`, to understand a top-level 1:1 `moved_from` mapping:

```json
"moved_from": {
  "<new entry key>": "<old entry key>"
}
```

The mapping is top-level rather than stored inside an entry. Existing sentries consume
`entries` and some compare each entry exactly with a derived `{reason, exit}` record, so adding
metadata to an entry would break those sentries. There is one parser and one comparison path;
the CLI script continues to load `_ratchet.py` and does not grow a second implementation.

For a newly gained key, the checker accepts a move only when the new key is in the head, the
old key was in the merge base and is absent from the head, no two new keys name the same old
key, and the old base entry equals the new head entry exactly. The equality includes `reason`,
`sites`, `exit` and any future members. A move cannot hide growth: the entry count of each of
the two affected baselines remains exactly unchanged in this PR, all four old keys disappear,
all four new keys appear, and the existing union-growth checks still run after applying the
1:1 substitutions.

The first commit adds positive tests for one and several exact moves and negative tests for an
old key still present, duplicate old targets, a missing old key, a mapping whose new key is
absent, unequal entry payloads, a raised `sites` value, and a non-object `moved_from` mapping.
Stored-type cells refuse an empty or whitespace-only key or value and any non-string value,
including a list, number, boolean or null, without crashing. Tests also assert the report
counts are unchanged.
The later mechanical move commit adds the four top-level mappings to
`private-file-sinks.json` and `atomic-writer-allow.json` with no entry-payload or count change.
The atomic-writer reason already expects a later rename, and H-1 will reuse the same checked
mechanism when `_sources.py` moves.
