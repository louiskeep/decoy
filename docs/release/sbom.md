# SBOM (CycloneDX)

**Status:** generator implemented (release readiness R1-c). The SBOM is not signed,
published or attached to any release; that wiring belongs to the release workflow.

`scripts/release/sbom.sh` writes a CycloneDX 1.6 JSON SBOM for the pinned third-party
runtime that the CLI bundle ships with.

```bash
scripts/release/sbom.sh                                   # requirements-certified.txt -> ./sbom.cdx.json
scripts/release/sbom.sh requirements-certified.txt out/sbom.cdx.json
```

Needs `uv` on PATH. **Network:** the first run downloads the tool's wheels from PyPI (and
CPython 3.12 if uv does not already have it); later runs reuse uv's cache, and an offline
host with a warm cache works. Nothing is added to `pyproject.toml` or the locks.

## Which pin list

`requirements-certified.txt`, the only runtime-profile pin list in this repo: the exact
67-package third-party closure of the certified DP runtime, with no dev tooling.
`requirements-dev.lock` is the dev profile: the script refuses it by the
`#    scripts/dev/lock.sh` header that `scripts/dev/lock.sh` writes into it, whatever the
file is called. The bundle builder
(`packaging_tools/build_bundle.py`) installs wheels handed to it by the release pipeline
and reads no lock itself, so this file is the closest thing to a runtime lock.

Not in this SBOM: `decoy-engine`, `decoy-engine-native` and `decoy-cli` are the bundle's own
wheels, not third-party pins. The root component is always `decoy-cli`, read from the repo
root's `pyproject.toml` whichever pin list is given (its `[project]` `name` and `version`
are required);
the engine's SBOM is generated by the `decoy-engine` repo's own `scripts/release/sbom.sh`
(a different script: it reads that repo's `uv.lock`, not a requirements file).

## How it is built

The upstream `cyclonedx-py requirements` tool reads the pin list, writes the SBOM and
validates it against the CycloneDX schema. The format is never hand-written.

The tool itself is pinned end to end. `scripts/release/sbom-tool-requirements.txt` is the
fully resolved, hashed environment of `cyclonedx-bom==7.6.0` and `cyclonedx-python-lib==11.12.0`
plus every transitive dependency (CPython 3.12, universal markers, wheels only). Each run:

- creates a throwaway venv and refuses any interpreter but CPython 3.12;
- checks the tool file's grammar with that bare interpreter before uv reads it (hashed
  `name==version` pins and comments only: no index, find-links or trusted-host options,
  URLs or paths);
- installs it with `uv pip install --require-hashes --no-deps --only-binary :all:`, so
  nothing is resolved or built at run time and a changed or tampered release fails;
- runs the tool as `python -I -m cyclonedx_py`, so `PYTHONPATH` and user site cannot
  shadow the hashed packages.

Every `uv` call passes `--no-config`, and the script drops every `UV_*` variable except
`UV_CACHE_DIR`, `UV_NATIVE_TLS` and `UV_HTTP_TIMEOUT` (`--no-config` skips `uv.toml` files
but not `UV_*` variables such as `UV_INDEX_URL`). Regenerate the tool file, after editing
the pins in `scripts/release/sbom-tool-requirements.in`, with:

```bash
scripts/release/sbom-tool-lock.sh
```

(needs network; review the diff and rerun `tests/unit/test_sbom_script.py`.)

## What the output holds

- One component per pin: name, version and `pkg:pypi` purl. The pin list has no hashes, so
  components have none (a hashed pin list would carry them).
- No license for third-party components: the pin list carries none and the generator reads
  it only. The dependency graph is flat (the requirements input has no edges).
- Package names only: no paths, hostnames, environment values, timestamps or serial number.

## Reproducibility

`--output-reproducible` removes `serialNumber` and `metadata.timestamp`, and the script
unsets `SOURCE_DATE_EPOCH` so the environment cannot put a timestamp back. Same pin list and
same tool pins give byte-identical output.

## Refusals

The script exits non-zero and writes nothing when:

- the arguments are not `[PINS [OUT]]` or `--validate FILE` (a usage message);
- the pin list is missing, or is anything but a well-formed sequence of `name==version
  [; marker]` pins, their `sha256` hash lines, whole-line comments and blanks (index URLs,
  paths, git or direct URLs, `-r`/`-e`, inline comments, options after a marker, orphan or
  dangling hash lines);
- the pin list holds any character outside printable ASCII and `\n`: `\r` (so CRLF), the
  other separators `str.splitlines()` honours, tabs and non-ASCII text, which the parser
  inside `cyclonedx-py` would split or decode differently from the check;
- a version is not canonical PEP 440, or a pin does not re-parse with
  `packaging.requirements.Requirement` as exactly `name==version [; marker]`;
- the pin list has no pins, or two pins for one PEP 503 name (duplicate or multi-version);
- the pin list is the dev-profile lock (its `scripts/dev/lock.sh` header);
- `pyproject.toml` at the repo root is missing or lacks `[project]` `name` or `version`;
- the generated SBOM's components are not exactly the pins (PEP 503 name and PEP 440
  version, counted), so a line the tool drops or reads differently (for example under a
  `# coding:` declaration) is a hard failure, not a silent omission;
- the tool requirements file is missing, breaks the grammar above, lacks a hash, any hash
  does not match, or a dependency has no wheel; or the venv interpreter is not CPython 3.12.

Whole-line comments are accepted but never reach the output. Error messages name files by
basename only.

## Tests

`tests/unit/test_sbom_script.py`: schema validation, completeness against the pin list
(component count equals pin count), hashes, PEP 503 names and `pkg:pypi` purls,
byte-identical reruns, leak canaries, the refusals above, run-time isolation (`PYTHONPATH`
shadowing, `uv.toml` and `UV_*` index overrides, a different interpreter, an sdist-only
dependency, `CDPATH`), and that every command in this page runs. It needs `uv` and network
on first use.
